# 小红书页面机制与 crawler 机制讨论

## 1. 目的

本文先把两件事分开说明：

1. 小红书信息流页面如何创建卡片、进入视口和加载真实帖子内容；
2. 当前 crawler 如何发现、滚动、处理和停止。

当前遇到的“最后几次滚动加载是空的”不是单纯的等待时间问题，而是流水屏的动态 DOM、懒加载状态与 crawler 对 DOM 的理解不一致。

## 2. 小红书信息流的基本机制

### 2.1 页面初始加载的不是完整帖子集合

小红书的信息流通常采用懒加载和分批加载：

- 页面先创建信息流容器；
- 容器中出现若干帖子卡片的 DOM 外壳；
- 卡片进入浏览器可视范围附近后，前端才触发数据请求、图片请求或卡片渲染；
- 卡片渲染完成后，才出现帖子链接、标题、点赞数等真实内容；
- 用户继续向下滚动后，前端再请求和创建后续卡片。

因此，以下状态必须区分：

| 状态 | DOM 中可能存在 `section` | 存在真实帖子链接 | 可以被 crawler 处理 |
| --- | ---: | ---: | ---: |
| 尚未创建 | 否 | 否 | 否 |
| 已创建骨架 | 是 | 否 | 否 |
| 已进入加载范围 | 是 | 不一定 | 不一定 |
| 帖子内容完成 | 是 | 是 | 是 |
| 重复或旧卡片 | 是 | 是 | 否，取决于去重结果 |

关键点是：`section` 数量只能说明页面创建了多少个候选节点，不能说明有多少个真实帖子已经准备好。

### 2.2 流水屏不会“滚到底”

小红书的信息流不是一个可以一次滚到底的静态列表，而是持续供给内容的流水屏：

- 向下刷时，底部不断出现新的卡片或骨架；
- 向上刷掉的旧卡片可能从 DOM 中删除、复用或替换；
- 当前 DOM 中的 `section` 数量只代表当前窗口附近的节点，不代表本次浏览已经见过的帖子总数；
- DOM 节点下标不是稳定的帖子编号，同一个 `section` 节点也可能在生命周期中承载不同内容。

因此，crawler 不能把“页面到底”作为正常结束条件。

任务应由 crawler 自己的配额控制，例如 `surface_max_posts`。连续几次没有发现新的真实 post ID，只能作为页面加载异常或无法继续前进时的保护性退出条件。

### 2.3 “可视范畴”是加载条件的一部分

这里的“进入可视范畴”不一定严格等于元素已经完全出现在 viewport 内。前端可能使用以下任一种范围：

- 元素实际进入 viewport；
- 元素距离 viewport 较近的预加载区域；
- 页面滚动容器的可视区域，而不是浏览器窗口的可视区域；
- 卡片内部图片或子节点进入观察范围。

所以 crawler 调用 `scrollIntoView()` 后，还需要等待前端异步完成。`scrollIntoView()` 只改变滚动位置，它本身不保证帖子数据已经渲染完成。

### 2.4 骨架节点会造成两个假象

#### 假象一：节点数量增加，认为加载成功

页面可以先批量创建多个空 `section`。此时：

```text
section 数量增加
!=
真实帖子数量增加
```

如果 crawler 用 `section` 数量判断滚动是否产生新内容，就会把骨架增长误认为有效加载。

#### 假象二：节点已经可见，认为帖子已经可处理

Playwright 的 `locator("section").wait_for(state="visible")` 只能说明该 section 满足可见性条件。它不能保证以下内容已经存在：

- `/explore/<post_id>` 链接；
- `.title`；
- `.count`；
- 图片地址；
- 点击后可打开的详情内容。

因此，帖子卡片的“可见”和“数据就绪”是两个不同的条件。

## 3. 当前 crawler 的机制

### 3.1 当前遍历对象

当前 crawler 在 `crawler/main.py` 中使用：

```python
posts = page.locator("css=.feeds-container").locator("section")
```

这表示 crawler 把信息流容器下的所有 `section` 当作帖子候选项。它没有在 locator 层面限制真实帖子链接，因此骨架节点也会进入遍历序列。

### 3.2 当前一次帖子处理流程

`grab()` 的一轮处理大致如下：

```text
读取当前动态 section 数量
  |
  | post_index 已经到达当前数量
  v
鼠标向下滚动，促使流水屏加载下一批内容
  |
等待 wait_scroll_multiplier
  |
重新读取当前窗口中的 section
  |
按真实 post ID 判断是否出现新内容
  |
继续遍历，或触发保护性停滞退出
```

如果当前索引还没有超过 section 数量，则流程是：

```text
取出第 post_index 个 section
  |
start_operation()
  |
scrollIntoView(block="center")
  |
等待 section visible
  |
等待真实 /explore/ 链接出现
  |
读取帖子 ID、标题、点赞数和图片
  |
点击帖子并读取详情
  |
关闭详情
  |
完成 operation
```

这里有两个不同层次的滚动：

1. `post_index >= total` 时使用鼠标滚轮，目的是让流水屏继续产生后续卡片；
2. 处理具体卡片时使用 `scrollIntoView()`，目的是让该卡片进入加载范围。

两种滚动都可能触发懒加载，但它们都必须通过真实帖子 ID 或真实内容状态验证结果。

### 3.3 动态 DOM 下标的风险

当前代码使用 `post_index` 配合动态 locator 下标：

```python
post = posts.nth(post_index)
post_index += 1
```

这在静态列表中可以工作，但流水屏回收上方卡片后存在两个问题：

- 上方节点删除后，后面的节点会前移，固定下标可能跳过帖子；
- 节点被前端复用后，同一个下标可能对应另一篇帖子。

因此，`post_index` 只能表示当前 DOM 窗口中的遍历位置，不能表示全局帖子序号。全局进度必须由本次任务已经发现或处理过的 post ID 集合维护。

### 3.4 当前滚动停滞条件

旧逻辑使用前后两次 `section` 数量判断是否停滞：

```python
new_total = await posts.count()
stagnant_rounds = stagnant_rounds + 1 if new_total <= total else 0
```

这个条件只能表达：

> 连续几轮没有新增 section，当前加载没有继续推进。

它不能表达：

> 页面已经到底，或者不存在更多帖子。

因为小红书本身不是以“到底”作为正常终点的页面。

当前代码已经改为用能解析到的真实帖子 ID 判断滚动是否有效，但这个判断仍需要通过实际页面日志验证：页面是否会在滚动后短暂返回重复 ID、是否会替换卡片节点，以及真实 ID 是否在进入视口后稳定存在。

## 4. 两套状态机的错位

### 4.1 小红书页面状态机

```text
未创建卡片
  -> 创建骨架
  -> 卡片进入预加载范围
  -> 请求帖子数据
  -> 填充真实链接和文字
  -> 可点击详情
  -> 继续加载下一批
  -> 回收离开视口的旧卡片
```

### 4.2 crawler 当前关注的状态机

```text
section 不存在
  -> section 数量增加
  -> section visible
  -> 等待真实链接
  -> grab_info()
  -> 点击详情
  -> 关闭详情
```

两者的主要错位是：

```text
小红书：真实内容填充完成
crawler：section 已经存在或可见
```

`section visible` 只能作为滚动动作完成的信号，不能作为帖子数据加载完成的信号。真正的处理前置条件应该是稳定取得帖子 ID，之后再读取标题、点赞数等字段。

另外，页面的动态节点变化意味着 crawler 不能依赖某个 section 永久存在。一个已经向上刷掉的帖子，即使仍然属于“本次任务已经处理过的历史”，也可能已经不在 DOM 中。

## 5. 为什么日志中会出现最后几次空滚动

以任务当前已经处理了一批真实帖子为例：

```text
已经处理若干真实帖子
  |
post_index 到达当前动态 section 数量，或当前窗口中的节点发生回收
  |
鼠标滚动，尝试让流水屏继续生成下一批卡片
  |
页面增加骨架 section、复用节点，或没有增加可用帖子
  |
等待约 5 到 7 秒
  |
再次检查真实 post ID
```

如果某一轮只是增加骨架，旧的数量判断会把它看作进展。如果改用真实 ID 判断，则这一轮属于停滞轮次。如果上方节点被回收，`section` 数量保持不变或减少，也不能说明页面到底，只能说明当前 DOM 窗口发生了变化。

只有达到保护性停滞阈值，或者达到 `max_posts` 配额后，`grab()` 才会结束。这个阈值不是在证明流水屏已经到底，而是在避免页面加载异常时无限滚动。

因此最后几条“滚动加载”记录表示 crawler 在等待流水屏继续产生可处理帖子，不表示页面存在一个可确认的底部，也不表示每次滚动都成功加载了新帖子。

这些滚动等待没有 operation 编号，是因为它们发生在 crawler 取得具体帖子之前，属于 task 级等待。这与任务分析设计中的定义一致。

## 6. 当前实现的正确边界

### 6.1 候选节点

`section` 可以继续作为页面结构的候选节点，但不能直接作为“已加载帖子”的证明。

### 6.2 真实帖子识别

当前真实帖子的最小识别条件是存在类似：

```text
a[href*="/explore/"]
```

并且可以从 href 中稳定提取 post ID。post ID 是比 DOM 节点数量和 DOM 下标更可靠的去重和进度指标。

### 6.3 处理前等待

处理某个候选节点时，至少要按以下顺序：

```text
section 进入视口
  -> 等待 /explore/ 链接出现
  -> 提取稳定 post ID
  -> 再读取标题、点赞数和图片
  -> 再执行点击详情
```

如果在合理时间内没有出现真实链接，该节点应被视为“骨架未完成”或“加载失败”，不能直接当成有效帖子。

### 6.4 滚动进度

滚动进度应优先使用：

```text
滚动前后的可解析唯一 post ID 集合是否增加
```

而不是：

```text
滚动前后的 section 数量是否增加
```

这里的“新 ID”应相对于本次任务已经处理或发现的 ID 集合判断，而不是相对于当前 DOM 判断。当前 DOM 会因为流水屏回收而缩小，不能作为历史集合。

### 6.5 任务结束条件

正常结束条件：

```text
成功处理数量 >= surface_max_posts
```

保护性结束条件：

```text
连续若干次滚动和等待后，没有发现新的真实 post ID
```

保护性结束条件的含义是“当前页面无法继续提供新的可处理帖子”，可能原因包括网络失败、登录状态异常、页面滚动容器不对、接口限流或前端加载卡住。它不应被命名或解释为“滚动到底”。

## 7. 需要验证的实验

下面的实验比继续增加固定 sleep 更有区分度。

### 实验一：记录节点与真实链接数量

每次鼠标滚动后记录：

```text
section 总数
可解析 /explore/ 链接数
唯一 post ID 数
当前 viewport 附近可解析 ID
```

目的：确认空滚动究竟是骨架增加、重复帖子增加，还是页面完全没有变化。

### 实验二：单个骨架节点的加载时序

对一个尚无 `/explore/` 链接的 section：

1. 记录进入 `scrollIntoView()` 的时间；
2. 轮询该 section 是否出现真实链接；
3. 记录出现链接、标题、图片和可点击状态的时间；
4. 比较这些时间与当前 `wait_post` 的关系。

目的：确认应该等待哪个 DOM 信号，以及 10 秒超时是否足够。

### 实验三：区分重复节点和新节点

每次滚动后输出新发现的 ID：

```text
new_ids = loaded_ids - known_ids
```

目的：确认页面是否会重新创建已经出现过的帖子节点，以及节点回收后是否会出现重复帖子。

### 实验四：确认滚动容器

检查实际滚动的是浏览器窗口还是信息流内部容器：

- 记录 `window.scrollY`；
- 记录 `.feeds-container` 的滚动属性；
- 记录目标 section 的 bounding box；
- 对比鼠标滚轮和 `scrollIntoView()` 的效果。

目的：避免 crawler 滚动了错误的容器，导致卡片始终停留在骨架状态。

## 8. 后续实现方向

当前应保持三个判断独立：

1. **节点存在**：页面创建了候选 section；
2. **帖子就绪**：section 内出现可解析的真实 post ID；
3. **处理成功**：详情打开、数据读取并关闭详情成功。

推荐的后续实现顺序是：

1. 保留真实帖子链接等待，避免直接处理骨架；
2. 使用真实唯一 post ID 判断滚动是否有进展；
3. 不依赖动态 DOM 下标表示全局进度；
4. 增加结构化的加载状态日志；
5. 根据实验结果决定是否需要等待标题、详情按钮或接口响应；
6. 最后再调整滚动距离、等待时长和停滞阈值。

不要把固定等待时间当作页面加载完成条件。固定等待只能控制节奏，不能证明小红书已经把目标帖子从骨架填充为真实内容。

## 9. 结论

小红书当前最重要的机制是：

```text
流水屏持续供给内容，卡片进入加载范围后才可能从骨架变成真实帖子，离开上方视口的卡片还可能被回收
```

当前 crawler 的核心问题是：

```text
用动态 section 的存在、数量和下标推断全局帖子进度
```

更准确的判断应该是：

```text
让候选卡片进入加载范围
  -> 等待真实 post ID 出现
  -> 用 post ID 做任务内去重和进度记录
  -> 达到任务配额后结束
  -> 连续无法获得新 ID 时仅作为保护性退出
```

最后几次“滚动加载”之所以看起来为空，是因为 crawler 在等待流水屏产生下一批可处理帖子，而不是在接近一个真实存在的页面底部。
