# 图片缓存机制与 URL 重复分析

## 1. 目的

Crawler 的图片缓存用于减少重复浏览时的图片网络传输。本文记录当前实现、命中次数的含义、WebUI 展示方式，以及相同视觉内容出现多份缓存的原因和后续优化条件。

## 2. 当前缓存流程

Crawler 启用 `image_strategy=cache` 后会拦截页面图片请求。

处理流程如下：

1. 使用请求的完整 URL 查询 MongoDB `image_cache` 集合；
2. 查询命中时，直接使用数据库中的 `data` 和 `content_type` 响应页面，不再请求远端图片；
3. 查询未命中时，请求远端图片；
4. 远端响应成功且内容类型受支持时，将 URL、图片二进制、内容类型和创建时间写入数据库；
5. `url` 字段有唯一索引，并发请求同一 URL 时不会保存多份文档。

`cache_image()` 显式缓存帖子图片时使用相同的按 URL 查询和写入机制。

## 3. 命中次数

`hit_count` 表示 crawler 实际复用 MongoDB 图片缓存的次数。

以下情况会增加一次：

- 页面加载图片时，路由拦截器按完整 URL 找到缓存；
- `cache_image()` 按完整 URL 找到已缓存图片。

以下情况不会增加：

- WebUI 加载缩略图或打开原图；
- WebUI 自动刷新缓存列表；
- 首次从远端下载并写入图片。

因此，`hit_count` 可用于观察缓存是否减少了 crawler 的重复网络请求，不代表图片在管理页面中的浏览次数。

## 4. 为什么会出现视觉上相同的缓存

当前缓存键是完整 URL，不是图片内容哈希。只要 URL 不同，系统就会将其视为不同的远端资源。

已观察到的小红书头像 URL 使用七牛 CDN 图片处理指令，例如：

```text
https://sns-avatar-qc.xhscdn.com/avatar/<resource-id>?imageView2/2/w/120/format/jpg
https://sns-avatar-qc.xhscdn.com/avatar/<resource-id>?imageView2/2/w/120/format/webp
https://sns-avatar-qc.xhscdn.com/avatar/<resource-id>?imageView2/2/w/120/format/webp!imageMogr2/strip
```

稳定部分是域名和 `/avatar/<resource-id>` 路径。变化部分包含：

| 指令 | 含义 |
| --- | --- |
| `imageView2/2` | 图片缩放模式 |
| `w/120` | 输出宽度为 120 像素 |
| `format/jpg` | 输出 JPEG |
| `format/webp` | 输出 WebP |
| `imageMogr2/strip` | 删除图片元数据 |

这些 URL 可能产生视觉上相同或非常接近的图片，但格式或二进制内容并不一定相同。按完整 URL 缓存时，它们会分别保存，并在后续请求各自的完整 URL 时分别命中。

## 5. 当前方案的实际影响

对于重复浏览，页面通常会再次生成相同的完整 URL，因此现有缓存仍然可以命中并避免远端传输。

当前方案的主要代价是：

- 同一原图的 JPEG、WebP 或不同处理版本可能重复占用数据库空间；
- 第一次遇到每种 URL 变体时都需要下载；
- 如果 URL 包含每次变化的签名、时间戳或随机参数，则可能持续无法命中。

当前已收集样本主要是稳定的 CDN 图片处理指令，没有证据表明参数会在每次浏览时随机变化。因此暂时保留完整 URL 作为缓存键，避免错误合并不同尺寸、裁剪方式或格式的响应。

## 6. URL 规范化与内容哈希的区别

### 6.1 URL 规范化

URL 规范化发生在发起远端请求之前。它可以忽略已确认不影响使用结果的参数，使不同 URL 变体共享缓存，从而直接减少网络传输。

风险是错误忽略影响尺寸、裁剪、质量或格式的参数，导致 crawler 返回与页面请求不一致的图片。

### 6.2 内容哈希

内容哈希需要先下载完整图片，再计算 SHA-256 等摘要。它可以合并二进制完全相同的内容并减少数据库占用，但无法避免首次重复下载。

如果两个 URL 分别返回 JPEG 和 WebP，即使视觉内容相同，二进制哈希通常也不同。内容哈希不能用于识别这种视觉相似图片。

因此：

| 目标 | 合适方案 |
| --- | --- |
| 减少重复网络传输 | 请求前 URL 规范化 |
| 合并二进制完全相同的缓存 | 内容哈希 |
| 合并视觉相似但编码不同的图片 | 感知哈希，但不适合作为请求前缓存键 |

## 7. WebUI 支持

WebUI 的“图片缓存”页面用于观察缓存行为，当前展示：

- 图片缩略图；
- 内容类型和文件大小；
- 创建时间；
- crawler 命中次数；
- 来源 URL；
- 拆分后的 URL 查询参数。

图片列表分页加载。自动刷新会合并最新数据，并保留已经加载的分页、滚动位置和展开的 URL 分析区。

## 8. 后续优化条件

在修改缓存键之前，应先通过 WebUI 和 `hit_count` 收集数据。满足以下任一情况时，再考虑 URL 规范化：

- 大量视觉重复图片的 `hit_count` 长期为 0；
- 同一资源路径频繁出现仅签名、时间戳或随机参数不同的 URL；
- 图片缓存集合增长速度明显快于实际浏览内容；
- MongoDB 图片数据占用成为实际问题。

实施 URL 规范化时应按 CDN 域名分别定义规则，不应对所有 URL 全局删除查询参数。尺寸、裁剪和质量参数默认保留，只有经过样本验证的干扰参数才可忽略。
